Зачем системный подход?

Классический подход к созданию карточек — интуитивное заполнение Description. Системный подход — причинно-следственная архитектура, где каждый элемент производит наблюдаемое действие. Разница измерима.

ПараметрКлассический подходСистемный подход (SPINE)
Дрейф голоса (20+ сообщений)~40% отклонение от исходного тона~10% отклонение при том же токен-бюджете
Консистентность поведенияМодель заполняет пробелы дефолтамиЯкоря (Anchors) задают конкретные триггеры → модель следует паттернам
Токен-эффективностьDescription (Описание) = 500+ токенов общих характеристикOCEAN: N:68 = 5 токенов вместо 30 текста
Динамика персонажаСтатичное поведениеWANT→NEED сдвиг через Price — персонаж развивается в сессии

Методология: проценты в гайде — эмпирические ориентиры на основе тестирования ~50 карточек на 12B–32B моделях с 32K-словарём (ранние Llama 2, Qwen 1.x, ранний Mistral). Для актуальных 12B–14B моделей со словарём ≥128K (Gemma 3, Qwen 2.5, Mistral Nemo) разрывы меньше. Читайте их как качественные маркеры — стабилен / дрейфует / сломан, — а не как точные измерения.

Три ключевых принципа

Эти принципы обязательны для всех карточек: нарушение любого из них ухудшает генерацию, и никакие другие настройки это не компенсируют.

ПРАВИЛО: Фундаментальный принцип: LLM = сопоставитель паттернов (Pattern Matcher), не исполнитель правил. Директива в SP без паттерна в Examples нестабильна на моделях ≤14B (~40–60% следование директивам). Поэтому Examples — главный инструмент, а Description — логика поведения.

  1. Якорь = триггер → действие → цена. Поведение задаётся якорями, и у каждого якоря есть цена — физическая реакция, наблюдаемая в той же сцене. Без цены якорь остаётся инструкцией: модели нечего скопировать.
  2. Голос — только в Examples и Greeting. Характер речи модель считывает из примеров диалога, а не из описания. Лингвистический голос (слова, синтаксис, лексика, ритм) живёт в Examples; физическая характеристика голоса (тембр, хрип, механический гул) — часть телесности в Description.
  3. Психология — в Description, компактно, в тегах. SPINE, OCEAN и Enneagram размещаются в Description как структурированные теги (<spine>, <ocean>, <enneagram>) с числами и короткими пометками, а не развёрнутым текстом. В System Prompt психологии нет места.

ПРИМЕР: компактный и нарративный формат OCEAN в Description.

✓ <ocean>O:72 C:65 E:41 A:38 N:68</ocean> — пять чисел; модель считывает их как pattern, экстремумы помечаются короткой пометкой после чисел.

✗ «Елена — любопытная и творческая журналистка, склонна к конфликту и сарказму, тревожная и реактивная…» — нарратив: токены потрачены, структурной ясности нет.

Если в карточке есть SP, Description, Examples, Greeting — она уже работает: это и есть минимальная рабочая карточка, минимум — четыре блока. Три правила (якорь = T→A→P, голос только в Examples, психология только в Description) — единственное, что нельзя нарушать.

Профиль сборки: шесть вопросов

Ответьте на шесть вопросов до начала работы: они определяют, какие инструменты понадобятся и насколько большой будет карточка.

РЕКОМЕНДАЦИЯ: Если вы впервые собираете карточку — выбирайте «12B / 8K / Простая / 1 GHOST / без CoT / без Lorebook». Это конфигурация Елены: пять чисел OCEAN, одна строка на элемент SPINE, шесть якорей — три базовых и три FLAW-linked. Бюджет профиля — ориентир 400–900 токенов. Не пытайтесь сразу строить экспертную карточку: перегрузка Description и утечка голоса — самые частые последствия.
