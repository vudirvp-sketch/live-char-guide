## 1.1 Зачем системный подход?

`data-section: p1_value_proposition`

<!-- difficulty: BASIC -->

Классический подход — интуитивное заполнение Description. Системный подход — причинно-следственная архитектура, где каждый элемент производит наблюдаемое действие. Разница измерима.

| Параметр | Классический подход | Системный подход (SPINE) |
|----------|---------------------|---------------------------|
| Дрейф голоса (20+ сообщений) | ~40% отклонение от исходного тона | ~10% отклонение при том же токен-бюджете |
| Консистентность поведения | Модель заполняет пробелы дефолтами | Якоря (Anchors) задают конкретные триггеры → модель следует паттернам |
| Токен-эффективность | Description = 500+ токенов общих характеристик | OCEAN: `N:68` = 5 токенов вместо 30 текста |
| Динамика персонажа | Статичное поведение | WANT→NEED сдвиг через Price — персонаж развивается в сессии |

**Методология:** проценты и другие количественные оценки в гайде — эмпирические ориентиры на основе тестирования ~50 карточек на 12B–32B моделях с 32K-словарём (ранние Llama 2, Qwen 1.x, ранний Mistral). Для актуальных 12B–14B моделей со словарём ≥128K (Gemma 3, Qwen 2.5, Mistral Nemo) разрывы могут быть меньше указанных. Воспринимайте как качественные маркеры (стабилен / дрейфует / сломан), не как точные измерения.

Гайд учит строить карточку как поведенческий движок.

## 1.2 Базовые блоки карточки

`data-section: p1_card_overview`

<!-- difficulty: BASIC -->

**Карточка персонажа** — документ, задающий поведение ИИ-модели при ролевой игре. Думать о ней нужно как о **поведенческом движке**: каждый элемент производит наблюдаемое действие, а не украшает описание. Карточка состоит из пяти блоков, каждый выполняет свою функцию.

[VS: E01 — Card Anatomy. Стек из 5 блоков карточки (System Prompt / Description / Examples + Anchors / Greeting / Lorebook) с токен-аннотациями «мин/стд/макс» и сводной таблицей бюджета. Значения бюджета общие с канонической таблицей §7A.12 (SHARED_REFERENCE): блок Examples показывает итог — бюджет на один пример × количество примеров; строка Lorebook — объявленная оценка («Est.», Part 7B), не каноническое значение. Замещает текстовое перечисление структуры блоков карточки.]

**Сквозной пример:** На протяжении всего гайда строим карточку Елены — от базовых блоков до полной карточки со всеми инструментами. Это позволяет увидеть, как каждый инструмент добавляет глубину персонажу.

**ПРАВИЛО:** О примерах и стиле. Этот гайд учит механике, не эстетике. Все примеры намеренно сухие — они иллюстрируют структурные принципы (причинность SPINE, триггеры поведенческих якорей, маркеры Voice, логику CoT), а не качество письма. Когда пример содержит нарративный язык («Дождь барабанил по стеклу»), он существует для демонстрации конкретной директивы (в данном случае Environmental Reactivity) и помечен соответствующим образом. Стиль вашего персонажа — качество прозы, глубина лора, сенсорная насыщенность — ваша предметная область. Гайд гарантирует, что модель её уважает.

## 1.3 Структурные свойства блоков

`data-section: p1_structure_overview`

<!-- difficulty: BASIC -->

Структура и содержимое блоков показаны выше в VS-EMBED E01 (Card Anatomy) — стек из 5 блоков с токен-аннотациями. Якоря визуально вложены в Examples-зону, но структурно — отдельный блок (`<anchors>`-тег), не часть диалоговых примеров. Таблица ниже — структурные свойства, не видные в viz: влияние на модель и качественная доля бюджета.

| Блок | Влияние на модель | Доля бюджета |
|------|-------------------|--------------|
| **System Prompt** | Высокое — задаёт рамки | Компактный |
| **Description** | Среднее — контекст | Основной объём |
| **Examples** | Ключевое — паттерны речи | Средний |
| **Якоря (Anchors)** (в Examples-зоне) | Ключевое — поведенческие триггеры | Средний (отдельный `<anchors>`-тег) |
| **Greeting** | Поддерживающее — тон | Минимальный |

Каждый блок карточки имеет токен-бюджет. Полная таблица лимитов и интерактивный калькулятор → `[ref: part_07a.md §7A.12 — Token Budget]`. Пошаговый конвейер сборки карточки на примере Елены → `[ref: part_07a.md §7A.13 — Assembly walkthrough]`.

## 1.4 Три ключевых принципа

`data-section: p1_core_rules`

<!-- difficulty: BASIC -->
<!-- canonical: Pattern Matcher rule, 3 key principles (Anchor=T→A→P, Voice only in Examples, Psychology only in Description) -->

Эти принципы обязательны для всех карточек. Нарушение любого из них приводит к ухудшению качества генерации.

**Ключевые термины (используются далее без повторного объяснения):**
- **Якорь (Anchor)** — конкретное правило поведения в формате Trigger → Action → Price. Подробно — Part 2.
- **Voice** (голос) — уникальный стиль речи персонажа; задаётся только в Examples и Greeting. Подробно — Part 3.
- **SPINE** — психологический каркас из 5 элементов (GHOST/LIE/FLAW/NEED/WANT). Подробно — Part 4.
- **OCEAN** — модель личности из 5 измерений (O/C/E/A/N). Подробно — Part 5.

**ПРАВИЛО:** Фундаментальный принцип: LLM = **сопоставитель паттернов (Pattern Matcher)**, не исполнитель правил. Директива в SP без паттерна в Examples нестабильна на моделях ≤14B (~40–60% следование директивам). Поэтому Examples — главный инструмент, а Description — логика поведения.

1. **Якорь = Trigger → Action → Price** — поведение задаётся якорями, и у каждого якоря обязательна Цена — физическая реакция в той же сцене. Без Цены якорь = инструкция без паттерна.
2. **Голос — только в Examples и Greeting** — модель считывает характер персонажа из примеров диалога, а не из описания. **Лингвистический голос** (слова, синтаксис, лексика, ритм фразы) — только Examples; **физическая характеристика голоса** (тембр, хрип, механический гул) — допустима в Description как часть Embodiment.
3. **Психология — в Description компактно, в тегах, не нарративом** — SPINE, OCEAN, Enneagram размещаются в блоке Description как структурированные теги (`<spine>`, `<ocean>`, `<enneagram>`) с числовыми значениями и короткими пометками, не развёрнутым текстом. Никогда в System Prompt.

**ПРАВИЛО:** Якоря — отдельный структурный блок внутри Examples-зоны карточки, не часть диалоговых примеров. Якоря размещаются как самостоятельный `<anchors>`-тег (в Description для большинства фронтендов, где нет отдельного поля Anchors) или как отдельное поле (в фронтендах с поддержкой). Концептуально якоря принадлежат Examples-зоне: их триггеры и паттерны влияют на генерацию наравне с диалоговыми примерами, но структурно они отделены от Examples — якоря = поведенческие паттерны, Examples = голосовые паттерны. → `[ref: part_02.md §2.2 — правила якорей]`, `[ref: part_07a.md §7A.13 — Assembly Pipeline]`.

<div class="callout ex">

**ПРИМЕР:** верный и неверный формат OCEAN в Description.

✓ `<ocean>O:72 C:65 E:41 A:38 N:68</ocean>` — числовые значения, компактно, модель считывает как pattern. Экстремумы и осторожная зона помечаются короткой пометкой после чисел.

✗ *«Елена — любопытная и творческая журналистка, склонна к конфликту и сарказму, тревожная и реактивная…»* — нарративное описание черт. Модель хуже считывает нарратив как поведенческий pattern; длинный текст расходует токены Description без структурной ясности.

</div>

Пример реалистичного современного персонажа (без фэнтези-элементов, простая SPINE) — Уолтер Уайт, `[ref: part_10.md §10.2]`.

## 1.5 Топ-3 критичные ошибки

`data-section: p1_top3_problems`

<!-- difficulty: BASIC -->
<!-- canonical: Top-3 critical errors (godmoding, wrong voice, ideal character) -->

Три самые частые ошибки начинающих, которые сильнее всего ломают качество карточки. Каждая разбирается подробно: симптом → причина → пошаговое исправление. Дополнительные проблемы → `[ref: part_09.md §9.2 — Таблица симптомов]`.

### Ошибка 1: Персонаж пишет за {{user}}

- **Симптом:** Модель описывает действия, мысли и реплики `{{user}}`. Диалог превращается в монолог от двух лиц.
- **Причина:** В System Prompt нет Anti-godmoding.
- **Исправление:** Добавьте в SP строку «Never speak or act for {{user}}.» → `[ref: part_08.md §8.2 — разбор AP-6]`.

### Ошибка 2: Голос не соответствует описанию

- **Симптом:** Вы описали персонажа как «лаконичного и холодного», но модель отвечает многословно и эмоционально.
- **Причина:** Голос помещён в Description вместо Examples (принцип #2 из §1.4). Модель — Pattern Matcher: она копирует паттерны из Examples, но почти не следует стилистическим директивам в Description.
- **Исправление:** Полный разбор → `[ref: part_03.md §3.1 — Voice Isolation]`.

### Ошибка 3: Персонаж «слишком идеальный»

- **Симптом:** Персонаж не проявляет уязвимость, не ошибается, реагирует «правильно» на все стимулы.
- **Причина:** Якоря не имеют цены (Price). Без физической реакции якорь = инструкция без паттерна (принцип #1 из §1.4).
- **Исправление:** Критерии качества якорей → `[ref: part_02.md §2.2 — правила якорей]`.

Если в карточке есть SP, Description, Examples, Greeting — она уже работает. Три принципа из §1.4 — единственное, что нельзя нарушать.

Готовые карточки разной сложности — Елена (базовая), Уолтер Уайт (базовая современная), Омнис-Зета (экспертная), Выщербленный (экспертная, мульти-персонажность) → `[ref: part_10.md]`. Карта всех персонажей → `[ref: appendix_character_map.md]`.

## 1.6 Чек-лист перед сборкой

`data-section: p1_prebuild_checklist`

<!-- difficulty: BASIC -->
<!-- canonical: Pre-build checklist (6 questions) — Build-mode entry instrument (build profile) -->

**Профиль сборки** — входной инструмент режима сборки (Build). 6 вопросов перед началом работы; каждый ответ определяет, какие инструменты понадобятся и сколько токенов заложить. Путь сборки по готовому профилю: конвейер — `[ref: part_07a.md §7A.13 — Assembly walkthrough]`, бюджеты блоков — `[ref: part_07a.md §7A.12 — Token Budget]`.

| # | Вопрос | Варианты | Что это определяет |
|---|--------|----------|--------------------|
| 1 | **Размер модели** | 12B / 32B+ / API | 12B — упор на Examples и Anchors, минимальный SP. 32B+ — можно CoT, Author's Note, Lorebook. API — максимум инструментов. → `[ref: appendix_model_params.md]`. |
| 2 | **Контекстное окно** | 4K / 8K / 16K+ | 4K — Description ≤200 токенов, 2 Examples. 8K — Description ≤400, 3 Examples, базовый Lorebook. 16K+ — полная карточка, CoT, слои призрака (GHOST Layers). → `[ref: part_07a.md §7A.12 — Token Budget]`. |
| 3 | **Сложность персонажа** | Простая / Средняя / Экспертная | Простая — Елена (`[ref: part_10.md §10.1]`), Уолтер Уайт (`[ref: part_10.md §10.2]`): четыре обязательных блока. Средняя — базовая структура плюс один продвинутый инструмент (CoT или Lorebook); отдельной карточки этого уровня в Part 10 нет. Экспертная — Омнис-Зета (`[ref: part_10.md §10.3]`), Выщербленный (`[ref: part_10.md §10.4]`): слои призрака + CoT + Lorebook. → `[ref: part_10.md]`. |
| 4 | **Призрак (GHOST): один или слои призрака** | 1 (одиночный) / 3-tier (слои) | 1 — обычная карточка, призрак = одно событие. 3-tier — временная хронология (детство → юность → настоящее). → `[ref: part_04.md §4.2 — слои призрака]`. |
| 5 | **CoT нужен?** | Нет (Tier 0 — только телесность) / Да (Tier 1+) | Нет — протокол телесности (Embodiment Protocol, State→Body→Sensor→Speech) достаточен как микро-цепочка рассуждений, отдельный `[INTERNAL]`-блок не нужен. Да — нужен явный внутренний монолог для SPINE-триггеров сверх телесности. → `[ref: part_06.md §6.2 — уровни CoT]`. |
| 6 | **Lorebook нужен?** | Нет / 1–3 записи / 5+ записей | Нет — все факты помещаются в Description. 1–3 — контекстные триггеры. 5+ — мир + факты призрака (GHOST). → `[ref: part_07b.md §7B.3 — Lorebook]`. |

**РЕКОМЕНДАЦИЯ:** Если вы впервые собираете карточку — выбирайте «12B / 8K / Простая / 1 GHOST / без CoT / без Lorebook». Это конфигурация Елены (та же, что в `[ref: part_07a.md §7A.13 — шаг 6]` и `[ref: part_10.md §10.1]`; бюджет по блокам — `[ref: part_07a.md §7A.12]`). Не пытайтесь сразу строить экспертную карточку — это ведёт к перегрузке Description и утечке голоса.
