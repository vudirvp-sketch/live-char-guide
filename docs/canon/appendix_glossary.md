## C.1 Глоссарий

`data-section: appendix_glossary`

<!-- difficulty: BASIC -->
<!-- canonical: Glossary (all term definitions) -->

Алфавитный справочник всех технических терминов, используемых в гайде. Каждый термин содержит определение и ссылку на канонический раздел, где он описан подробно.

### A — Anti-godmoding

**Anti-godmoding (анти-годмодинг)** — правило, запрещающее персонажу говорить или действовать за `{{user}}`. В шаблоне System Prompt оформляется двумя строками: запрет («Never speak or act for {{user}}») и позитивная формулировка («respond only to observable actions and words»). Позитивная формулировка работает лучше чистого запрета, поскольку даёт модели паттерн для подражания.

→ `[ref: part_07a.md §7A.X — System Prompt]`

### B — Behavioral Anchor

**Behavioral Anchor (поведенческий якорь)** — триггер-действие-паттерн (T→A→P), активирующий конкретное поведение. Anchor Format: Триггер (внешний стимул) → Действие (наблюдаемая реакция) → Цена (физическая реакция в той же сцене). Anchors — основной механизм задания характера без бесконечного описания; каждый FLAW требует минимум один FLAW-linked Anchor. **RULE:** Anchors — отдельный структурный блок внутри Examples-зоны карточки, не часть диалоговых примеров. В большинстве фронтендов размещаются как `<anchors>`-тег в Description; концептуально Anchors = behavioural patterns, Examples = voice patterns.

→ `[ref: part_02.md §2.1 — Behavioral Anchors]`

### C — CoT

**CoT (цепочка рассуждений)** — система рассуждений внутри карточки, направляющая модель через SPINE-осознанные решения. CoT добавляет пошаговый внутренний процесс, который модель воспроизводит перед генерацией ответа. Имеет четыре уровня сложности: Tier 0 (basic Anchor) — Tier 3 (полный XML-процесс для API). Не более 2–3 CoT Anchors на карточку.

→ `[ref: part_06.md §6.2 — CoT basics]`

### C — CORE DIRECTIVES

**CORE DIRECTIVES (базовые директивы)** — набор из 7 поведенческих директив внутри System Prompt. Формируют «операционную систему» генерации: связную логику, а не разрозненные инструкции. Пишутся на английском — на 12B моделях английские инструкции соблюдаются стабильнее (~15–20% выше следование директивам).

1. **Show Never Tell (#1)** — Эмоции и состояния демонстрируются через поведение, не рассказываются напрямую. Мета-принцип: Voice Isolation (показывай голос, не описывай), Embodiment (показывай эмоции через тело, не называй), Format Lock (показывай формат, не инструктируй).
2. **Embodiment First (#2)** — Поведенческая последовательность State → Body → Sensor → Speech всегда соблюдается. Директива-МАНДАТ, предписывающая всегда использовать Embodiment Protocol (Протокол описывает КАК, Директива — ОБЯЗАТЕЛЬСТВО).
3. **Spatial & Anatomical Lock (#3)** — Тело персонажа существует в физическом пространстве с консистентной анатомией и позиционированием. Отслеживать расстояние, позу, вес предметов, линию взгляда. Никакой телепортации, никаких анатомических противоречий.
4. **Environmental Reactivity (#4)** — Модель реагирует на стимулы окружения, описанные в сообщениях `{{user}}`. Сенсорные и пространственные детали вводятся органично через действие персонажа, никогда — декоративно. Среда раскрывается через действие, а не описывается отдельно от персонажа.
5. **Influence Boundary (#5)** — Персонаж не контролирует действия, мысли или эмоции `{{user}}`. Реагируйте только на наблюдаемые симптомы: можно заметить, что `{{user}}` вздрогнул, но нельзя заявить, что `{{user}}` напуган. Эффект персонажа на `{{user}}` — поведенческий триггер, не декларация факта.
6. **Consequence Driven (#6)** — Действия имеют необратимые последствия; нарратив отражает причину и следствие. WANT сдвигается к NEED по мере накопления Price в сессии. Базовое понимание — в SPINE-секции; полное отслеживание — через Author's Note с секцией WANT→NEED.
7. **Pre-Generation Filter (#7)** — Перед генерацией модель проверяет вывод на соответствие SPINE и Anchors. Чеклист перед каждым ответом: (1) Новый сенсорный элемент введён? (2) Реакция привязана к телу? (3) Влияние на `{{user}}` основано на наблюдаемых симптомах? (4) Ноль мета-комментариев?

→ `[ref: part_07a.md §7A.X — CORE DIRECTIVES]`

### E — Embodiment Protocol

**Embodiment Protocol (протокол телесности)** — поведенческая последовательность: Состояние → Тело → Сенсор → Речь. Каждый эмоциональный сигнал проявляется физически: внутренний вес/баланс → напряжение/дрожь → контакт со средой (текстура, звук, запах) → тон/темп/лексика. Отличается от директивы «Embodiment First» — Протокол описывает КАК (последовательность), а Директива — ОБЯЗАТЕЛЬСТВО (всегда использовать).

→ `[ref: part_02.md §2.X — Embodiment]`

### E — Enneagram

**Enneagram (эннеаграмма)** — 9-типная модель личности, сопоставляемая с элементами SPINE. Каждый тип имеет ключевой страх, ключевое желание, направление стресса и направление роста — что позволяет вывести LIE, WANT, FLAW и NEED из типа. OCEAN описывает «сколько» черты, Enneagram отвечает на «почему» персонаж действует именно так.

→ `[ref: part_05.md §5.4 — Enneagram]`

### F — FLAW

**FLAW (дефект)** — конкретное поведение персонажа, мешающее ему получить NEED. Рождается из LIE: ложная установка заставляет персонажа действовать саморазрушительно. FLAW — всегда наблюдаемое поведение, не прилагательное («отталкивает людей сарказмом» ≠ «циничный»). Каждый FLAW требует минимум один FLAW-linked Anchor.

→ `[ref: part_04.md §4.X — FLAW]`

### G — GHOST

**GHOST (призрак)** — формирующая травма или опыт прошлого, лежащий в основе цепочки SPINE. GHOST — конкретное событие, не психологический вывод. Это корень причинной цепочки: GHOST порождает LIE как защитный механизм от боли. Запрещённые слова в описании GHOST: «травма», «пережил», «столкнулся с».

→ `[ref: part_04.md §4.X — GHOST]`

### G — GHOST Layers

**GHOST Layers (слои призрака)** — 3-уровневая архитектура (G1=Детство, G2=Отрочество, G3=Настоящее) для сложной травмы. G1 формирует LIE, G2 укрепляет FLAW, G3 определяет текущие триггеры. Не всем персонажам нужны 3 слоя — если backstory простая, достаточно одного GHOST.

→ `[ref: part_04.md §4.X — GHOST Layers]`

### G — Greeting Message

**Greeting Message (приветственное сообщение)** — первое сообщение персонажа в разговоре, демонстрирующее Voice, SPINE и Anchors в действии. Строится по алгоритму: Sensory Anchor → тело FLAW → реплика → крючок. Длина: 50–100 токенов. Задаёт место, время и тон, но не сюжет.

→ `[ref: part_07b.md §7B.X — Greeting Message]`

### I — Identity Block

**Identity Block (блок идентичности)** — раздел System Prompt, определяющий, кто персонаж: имя, роль, ключевые черты. Оформляется одной строкой: «You are {{char}}. {{brief_identity}}». Занимает ~10 токенов; остальные черты уходят в Description как факты, не как голос.

→ `[ref: part_07a.md §7A.X — Identity Block]`

### L — LIE

**LIE (ложная установка)** — ложная установка, в которую верит персонаж, часто мешая получить NEED. Вытекает из GHOST как защитный механизм от боли. Оформляется как фраза в кавычках — то, что персонаж сказал бы о себе. LIE объясняет, почему существует FLAW: ложная установка заставляет действовать саморазрушительно.

→ `[ref: part_04.md §4.X — LIE]`

### L — Lorebook

**Lorebook (база знаний)** — система инъекции ключ-значение, вставляющая знания персонажа в контекст по требованию. Каждая запись содержит: Key (триггер-слово), Content (факт для вставки), Position (куда вставлять), Depth (глубина поиска). Особенно полезна для GHOST-связанных фактов и сенсорных активаций.

→ `[ref: part_07b.md §7B.X — Lorebook basics]`

### M — MBTI

**MBTI (типология Майерс-Бриггс)** — типология из 16 типов на основе 4 осей (E/I, S/N, T/F, J/P). Доступна как справочный инструмент в Appendix A. Для создания карточки рекомендуется использовать OCEAN (полюса → Anchors) и Enneagram (тип → SPINE); MBTI дополняет понимание, но не имеет прямого маппинга на SPINE.

→ `[ref: appendix_mbti.md §A.1 — MBTI]`

### N — NEED

**NEED (потребность)** — истинная потребность персонажа — то, что ему на самом деле нужно для роста. Часто противоречит WANT. FLAW блокирует NEED: именно поэтому персонаж не может получить то, в чём действительно нуждается. Обычно связано с людьми и связями; персонаж может не осознавать свою NEED.

→ `[ref: part_04.md §4.X — NEED]`

### O — OCEAN

**OCEAN (Большая пятёрка)** — модель личности: Openness (Открытость), Conscientiousness (Добросовестность), Extraversion (Экстраверсия), Agreeableness (Доброжелательность), Neuroticism (Нейротизм). Используется для проверки внутренней консистентности персонажа и дополнения фреймворка SPINE. Золотое правило: только 1–2 экстремальных полюса (значения <30 или >70). В карточке OCEAN размещается в Description как тег `<ocean>` с числовыми значениями, не нарративным описанием черт — см. принцип #3 (§1.4).

→ `[ref: part_05.md §5.1 — OCEAN]`

### S — SPINE

**SPINE (позвоночник)** — 5-элементная причинно-следственная цепочка: GHOST → LIE → FLAW → NEED → WANT. SPINE даёт Anchors причину существовать, а не быть набором случайных правил. Каждый элемент = наблюдаемая единица, не абстрактный ярлык. Для простых персонажей GHOST и LIE могут быть неявными, но при использовании полной цепочки она должна быть логически связана.

→ `[ref: part_04.md §4.1 — SPINE Overview]`

### S — System Prompt / SP

**System Prompt / SP (системный промпт)** — контейнер, вставляемый в начало контекста. Содержит: Identity Block, Anti-godmoding, CORE DIRECTIVES, блок SPINE, Tone Frame, Format Lock, OOC Protection. System Prompt — это КОНТЕЙНЕР; CORE DIRECTIVES — это СОДЕРЖИМОЕ (7 поведенческих директив внутри контейнера). SP — единственная техническая часть карточки, которую модель видит всегда.

→ `[ref: part_07a.md §7A.X — System Prompt]`

### T — T→A→P

**T→A→P (Trigger → Action → Price)** — формат Behavioral Anchor: Триггер (внешний стимул) → Действие (наблюдаемая реакция персонажа) → Цена (физическая реакция в той же сцене). T→A→P — базовая единица задания поведения в карточке; каждый Anchor обязан содержать все три элемента, иначе Anchor = инструкция без паттерна и модель его проигнорирует.

→ `[ref: part_02.md §2.1 — Behavioral Anchors]`

### T — Token Budget

**Token Budget (бюджет токенов)** — распределение токенов контекстного окна между компонентами System Prompt. Определяет, какие элементы карточки попадут к модели. Бюджет зависит от размера контекстного окна: 4K (~430–580 токенов на карточку), 8K (стандартный профиль), 16K+ и API (расширенный профиль).

→ `[ref: part_07a.md §7A.X — Token Budget]`

### V — Voice

**Voice (голос)** — лингвистический отпечаток персонажа: словарь, синтаксис, ритм, регистр. Голос = ритм + лексика + синтаксис + парадоксы. Ни один из этих компонентов не описывается прилагательными — только демонстрируется через Examples. Модель — копировщик паттернов, не исполнитель инструкций.

→ `[ref: part_03.md §3.X — Voice Isolation]`

### V — Voice Bleed (cross-character)

**Voice Bleed (переплетение голосов)** — режим отказа, при котором голос одного персонажа просачивается в речь другого. Возникает в мульти-персонажных сценах, когда модель начинает генерировать реплики одного персонажа в стиле другого. Предотвращается через минимум 3 голосовых маркера на каждого персонажа и явное различение голосов в Examples.

→ `[ref: part_03.md §3.X — Мульти-персонажные примеры]`

### V — Voice Bleed (degradation)

**Voice Bleed: деградация голоса (утечка голоса)** — деградация голоса одного персонажа — модель генерирует неверный голос (например, голос рассказчика или ассистента просачивается в речь персонажа). Возникает, когда стилистические директивы помещены в Description вместо Examples: модель не следует голосовым инструкциям, а копирует паттерны из примеров диалога. Предотвращается через Voice Isolation — голос задаётся ТОЛЬКО в Examples и Greeting, никогда в Description.

→ `[ref: part_03.md §3.X — Voice Leak / Voice Bleed]`

### V — Voice Isolation

**Voice Isolation (изоляция голоса)** — техника отделения Voice персонажа от Voice рассказчика и голосов других персонажей. Голос задаётся ТОЛЬКО в Examples и Greeting, никогда в Description. Для 12B моделей Description = 0% влияния на голос; стилистические директивы в Description — ошибка сборки.

→ `[ref: part_03.md §3.X — Voice Isolation]`

### W — WANT

**WANT (желание)** — осознанное желание персонажа — то, что он думает, что ему нужно. Внешняя цель, которую персонаж может сформулировать. WANT совместим с LIE: персонаж не видит противоречия между своим желанием и своей ложной установкой. Часто противоречит NEED, создавая нарративное напряжение.

→ `[ref: part_04.md §4.X — WANT]`
