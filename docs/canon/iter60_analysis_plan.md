## 1. Проблема: необоснованные английские термины

### 1.1 Контекст проблемы

Гайд использует смешанную русско-английскую терминологию. Языковая политика (`terminology_dictionary.md` §6) определяет:

- Русский — основной язык прозы
- Английский — каноническая форма для технических терминов  
- Первое упоминание — английский + русский перевод в скобках
- Заголовки/метки/`data-section` ID — всегда английский

**Пользовательский опыт:** русскоязычный читатель видит «Behavioral Anchor», «Embodiment Protocol», «Voice Isolation» в заголовках, хотя в беглом тексте эти же понятия звучат как «поведенческий якорь», «протокол телесности», «изоляция голоса». Двойная терминология создаёт когнитивную нагрузку без функциональной необходимости для большинства терминов.

### 1.2 Категоризация терминов

#### Категория A: ДОЛЖНЫ остаться английскими (функциональная причина)

Эти термины попадают в System Prompt карточки или являются кодоподобными идентификаторами в выходном артефакте. LLM-комплаенс на 12B моделях ~15-20% выше для английских директив — это измеримый, функциональный аргумент.

| Термин | Функциональная причина | Где используется |
|--------|------------------------|------------------|
| CORE DIRECTIVES (1-7) | Входят в SP карточки → LLM-compliance | §7A.2, SP template |
| System Prompt / SP | Карточный блок → technical identifier | Все Parts |
| SPINE / GHOST / LIE / FLAW / NEED / WANT | Акронимы в `<spine>` XML-тегах Description | §4.1-4.11, card output |
| OCEAN (O/C/E/A/N) | Числовые шкалы в `<ocean>` XML-тегах | §5.1-5.8, card output |
| T→A→P (Trigger→Action→Price) | Кодоподобная нотация Anchors | §2.1-2.3, card output |
| CoT / `<processus_analysium>` | AI-стандарт + XML-тег в card output | §6.1-6.6 |
| `<START>` | Код-маркер в Examples | §3.3 |
| RepPen / Presence Penalty / Top P / Min P / Top K | AI sampling parameters — стандарт индустрии | §7A.6 |

| Lorebook / LB | SillyTavern/frontend стандарт | §7B |

#### Категория B: МОГУТ стать русскими в заголовках (нет функциональной причины для английского)

Эти термины НЕ попадают в SP или card output. Английский используется только по аргументу «общепринято», который не подтверждён — это гайд-специфичные концепции, не индустриальные стандарты.

### 1.4 Конкретные изменения: terminology_dictionary.md

**Текущая проблема:** §1 маркирует русский перевод как ❌ «Запрещённые формы» для терминов, которые НЕ попадают в SP/card output.

**Решение: разделить «Запрещённые формы» на две категории:**

| Категория | Значение | Пример |
|-----------|----------|--------|
| ❌ Forbidden in code/ID/SP | Запрещено в `data-section`, XML, SP content | «системный промпт» → always «System Prompt» in code |
| ⚠️ Restricted as primary heading | Запрещено как PRIMARY заголовок, допустимо как русский эквивалент в скобках | «протокол телесности» → допустимо: «Протокол телесности (Embodiment Protocol)» |

**Новая языковая политика (§6 revision):**

1. Русский — основной язык прозы И заголовков секций.
2. English canonical — только для: (a) `data-section` ID, (b) XML-тегов в card output, (c) SP-содержимого, (d) акронимов (SPINE, OCEAN, SP, CoT).
3. Заголовки секций: русский первичный + English canonical в скобках при первом упоминании в Part.
4. Таблицы: русские заголовки.
5. Первый упоминание в Part: русский текст + English canonical в скобках (инверсия текущего правила).

**Invariant:** Изменение НЕ затрагивает `data-section` IDs, SP-содержимое, XML-теги, код-маркеры.

## 2. Проблема: повторения и низкая смысловая плотность

### Ключевой принцип (iter 60 revision)

**Гайд — единый последовательный документ, не википедия.** Читатель идёт сверху вниз и усваивает концепции по мере чтения. Поэтому:

- **Не повторять** концепции, уже объяснённые выше — просто использовать их.
- **Не добавлять `[ref:]`** кросс-референсы на каждый упомянутый термин — это загружает текст и делает его похожим на википедию, а не на единый гайд.
- `[ref:]` сохраняется только для навигационных указателей (Part 0 → Part 7A для конвейера сборки, Part 1 → Part 10 для готовых карточек) — не для повторных объяснений концепций.

### 2.1 Типы повторений

#### R1: Функциональные повторения (разные контексты, одна мысль)

Ранее планировалось заменять на `[ref:]` кросс-референсы. Новый подход: **не повторять**, а просто использовать концепцию, уже объяснённую выше в последовательном чтении.
