## 1. Purpose & method

**Problem being solved.** v1 is a single linear guide (Part 0 → Part 10 + 4
appendices) that implicitly serves four different reader jobs at once — study,
construction, diagnosis, lookup (research §23). The semantic-extraction stage
(iter 133–145) proved the underlying disease and its cure on seven bounded
clusters: **canonical knowledge lives once; every other form exposes,
demonstrates, or navigates to it** (foundation §5 INFERENCE). All seven clusters
now have a single canonical owner + a MUST-PASS parity gate. What does NOT yet
exist is the target architecture that the remaining migration stages (v2 build →
audits → switch) execute against — the reader-mode structure, the presentation
policies, the slice order, and the switch criteria. This document is that
architecture, assembled exclusively from verified inputs.

**Method.** No new research. Every section names its source; where two inputs
conflict, the conflict is surfaced as a ratification question rather than
silently resolved (AGENTS.md: the agent does not decide architecture semantics).
Nothing here edits v1: v1 stays the frozen migration source until the switch
(owner track directive, chat 2026-09-14).

**What this spec does NOT do.** No phase scope beyond P-a is opened; no v2 build
slice is defined as started; no v1 content is touched; no KI is re-classified;
no DEC-NN is assigned to spec items (that happens at ratification); the visual
system stays frozen per DEC-19.

## 3. Reader-mode specification (F1 — intake §5; research §23)

Four modes, per the owner directive (chat 2026-09-14) and research §23's model
(`Teach → learning · Apply → building · Verify → debugging · Reference →
lookup`). Per mode: entry point, default visibility, on-demand disclosure.
**Proposal: the modes are structural overlays on the same canonical content —
not four separate documents** (research §23: "this strengthens the existing
architecture rather than replacing it"; Editorial Policy: compress redundant
presentation, never unique capability).

| Mode | Reader job | Entry point (v2) | Default visibility | On-demand disclosure |
|---|---|---|---|---|
| **Learn** | Go through the method start-to-finish | Part 0 (how to read) → Part 1 → … linear order | Full narrative: concepts, rules, worked examples, transitions | Deep-dives/edge cases via F6 `<details>`; difficulty metadata (BASIC/INTERMEDIATE/EXPERT) already in place as the level filter |
| **Build** | Construct a card now | Part 7A §7A.13 assembly pipeline + §7A.12 budgets; Part 10 annotated blueprints | Templates (ШАБЛОН), budget tables, capability checklists (§7A.7), canonical value tables (§7A.6 etc.) | Why-explanations and concept teaching collapse into `<details>`/canonical links (Learn mode owns the teaching depth) |
| **Debug** | Diagnose a broken result | Part 9 §9.5 symptom table / §9.6 decision tree (E13) / §9.3 block checklist — already wired as the Debug chain (mig-3, iter 139) | Decision aids: symptom→check→diagnosis tables, AP cards (E12), one-change rule | Full per-AP breakdowns (§8.2–§8.16) and test scenarios (§9.7) on demand |
| **Reference** | Find one specific rule/term | Runtime glossary panel + no-JS `glossary.html` (generated, DEC-17/18); anchors/section IDs; appendices | Compact term/rule entries with canonical-home links | Full canonical definition one hop away (L1 owner section) |

**Mode backbones already exist in v1** (verified): the linear Part order +
difficulty metadata (Learn), the assembly pipeline + Part 10 blueprints (Build),
the §9.5/§9.6/§9.3 chain + E12/E13 (Debug), the glossary chain + section-ID
anchors (Reference). The v2 build therefore does **not** build four sites — it
applies the presentation policy (§4) per Part so each Part serves its primary
mode strongly and defers the others via disclosure + links.

**Ratification questions:** Q1 (mode set + entries/visibility as tabled above),
Q7 (KI#70 appendices wire/drop — the Reference-mode backbone question).

## 4. Presentation policy (F2–F6 — intake §5; applied per Part at its build slice)

### 4.1 Presentation-disposition vocabulary (F2)

Every block-level row of a Part being migrated gets a **presentation
disposition** — the per-Part redesign map, built on the existing 500-row matrix
(not a new audit):

| Disposition | Meaning | Typical target |
|---|---|---|
| `open` | stays visible in the page flow | canonical rules, core tables, key examples |
| `collapsible` | wraps in F6 `<details>` | why-explanations, edge cases, long worked examples, model-specific notes |
| `reference-relocate` | moves to the Reference layer (glossary/appendix) | term definitions living inside prose |
| `delete-candidate` | redundant presentation (Editorial Policy 5-point check passed) | matrix COMPRESS/DELETE rows |
| `canonical-link` | 1-sentence + link to the canonical owner | every non-owner restatement (fence #11 pattern) |

Application mechanism (proposed): a `presentation` column on the matrix rows of
the Part being sliced, filled at that slice's evidence step and executed in the
same slice — the same seed-then-execute pattern Registry C has used since iter
132. **Ratification question:** Q2.

### 4.2 Checklist triage (F3)

Three classes, no mixing (intake F3 / Analysis B2):
- **teaching** — a checklist that walks a concept (stays prose/list, no checkbox affordance);
- **decision-input** — a checklist that captures a build-profile choice (Part 1
  pre-build questionnaire: card goal, model class, SPINE depth — reframe as the
  Build-mode entry instrument);
- **validation** — a true pass/fail verification moment (checkboxes reserved
  here: §9.3 block checklist, §9.11 pre-deploy 5/14).

### 4.3 Example tiering (F4)

Two tiers: **inline** (no heading, no chip — woven into prose) and **worked**
(labelled ИЛЛЮСТРАЦИЯ/ПРИМЕР, full analysis). The Part 10 character cards stay
the canonical worked examples (EXAMPLE-139 family already verified by the
intake); ordinary illustrations default to inline unless they carry a distinct
recognition function (Editorial Policy).

### 4.4 Part micro-template (F5)

Per-Part section pattern (pattern-catalog candidate, applied at each Part's
build slice — not a mass rewrite):

```
Concept → Rule → Core example → ▸Why / ▸Common failure modes / ▸Edge cases / ▸Reference
```

The ▸-branches = F6 collapsibles; `Reference` = canonical-link row to the
glossary/related Parts. Existing sections already approximate this (the canon
README §3 conventions); the template regularizes the default, with Editorial
Policy's "tightly coupled rules may stay together" caveat.

### 4.5 Disclosure-component policy (F6)

`<details class="interactive">` (`docs/components.md` #5; 16 existing master
usages) = **the** sanctioned progressive-disclosure mechanism for v2. No new
infrastructure, no v8-style visibility tiers (intake F6: B7 + B10). Everything
the reader needs to *apply a rule correctly at that moment* stays `open`
(Editorial Policy: do not defer information whose absence causes incorrect
implementation).

## 7. v2 build plan (post-ratification)

**Unit of work:** one Part (or appendix) per iteration — the bounded-slice
discipline the seven executed clusters proved. Per-Part slice shape:

1. evidence step: seed the Part's matrix rows with F2 presentation
   dispositions (+ Registry C rows);
2. canon step: restructure the Part's canon sections per the F5 micro-template
   (Editorial Policy 5-point check per edit);
3. master step: mirror + apply F2 dispositions (F6 collapsibles, canonical
   links) + F3/F4 where the Part carries checklists/examples;
4. verification: full battery + the Part's new/extended parity checks.

**Proposed order (ratification question Q6):** guide order Part 1 → Part 10 →
appendices, because (a) Part 1 carries the F3 decision-input reframe (Build-mode
entry instrument) and the heaviest overload findings (intake §3); (b) each Part
reuses the previous slice's pattern; (c) Reference-mode backbone (glossary
chain) is already live, so no dependency blocks Part 1. Alternative (mode
backbone first) spends an iteration on wiring whose value is proven only after
the Parts exist — rejected by the same reasoning as P-c in the iter-144 package
§3.2.

**Explicitly out of build scope until their own owner calls:** version bump
(4-place fence #9), `data/anchor-redirects.json` changes (section-ID renames
break inbound links), KI#70 appendix wiring (rides the Reference/appendix
slice, Q7), any CSP/shell-infrastructure change.

## 8. Audit & switch plan (the pinned migration tail)

Stages, in the order the owner pinned (chat 2026-09-14; STATUS Next step):

1. **v2 build** — per-Part slices (§7), each leaving the battery green.
2. **parity audit** — the 7 cluster gates + sync + drift must pass on the
   completed v2 corpus; any new cluster discovered during the build gets its
   own gate before the stage closes.
3. **canonical audit** — one canonical home per concept across the whole guide:
   machine-checkable pass over the content map ↔ canon ↔ glossary registry
   (extends the KI#82-style Notes checks repo-wide).
4. **reader-path audit** — per mode (§3): entry point → task completion without
   leaving the mode's backbone (the iter-139 Debug reader-path audit
   `debug_readerpath_audit_iter139.py` is the executed precedent — replicate
   for Learn/Build/Reference).
5. **switch** — v2 becomes the live site. Proposed switch criteria (ratification
   question Q8): stages 2–4 green in two consecutive full-battery runs, no OPEN
   KI in the affected families, owner call. Mechanics per DEC-04 (root
   fallbacks regenerate; `build.hash` unchanged unless the shell changes).
