Как читать этот гайд

Вы собираете карточку персонажа: документ, который задаёт модели, кем быть, чего не делать и как отвечать. Готовая карточка ведёт себя предсказуемо — голос не сползает к дефолту модели, у поведения есть причина, а ошибку видно и можно исправить. Карточка состоит из пяти блоков:

БлокЧто в нёмГде учится
System PromptКто персонаж, чего он не делает, как думает, в каком формате отвечает7A
DescriptionФакты, психология (SPINE, OCEAN), физическое описание4–5 (SPINE, OCEAN), 7A.9 (XML)
ExamplesДиалоговые примеры; поведенческие якоря — отдельным тегом в Description2 (якоря), 3 (примеры)
GreetingПервое сообщение: место, время, тон7B
LorebookБаза знаний с триггерами — только если фактов не хватает Description7B

Обязательных блоков четыре. Lorebook добавляется, когда персонажу нужно больше фактов, чем помещается в Description.

Порядок чтения. Он в оглавлении: части идут слоями — сначала поведение (якоря, голос), потом психология (SPINE, OCEAN), и только затем сборка. System Prompt стоит после них не случайно: это контейнер, и его содержание выводится из предыдущих частей. Порядок сборки — другой: он в «Быстром старте» (часть 0) и в сборке System Prompt и Description (часть 7A).

  • Собираете прямо сейчас. Начните с «Быстрого старта»: шесть шагов минимальной карточки. Дальше идите по частям подряд — их порядок в оглавлении.
  • Карточка уже не работает. Начните с части 9 «Диагностика и тестирование»: от симптома к причине и исправлению.

Вот к чему мы идём. Ниже — минимальная версия карточки Елены: четыре обязательных блока и якоря на месте. Та же карточка целиком — в части 10, карточка Елены.

Примеры в гайде намеренно сухие: они показывают механику — причинность SPINE, триггеры якорей, маркеры голоса, — а не качество письма. Стиль, лор и сенсорная насыщенность остаются вашей предметной областью.

Быстрый старт: минимальная карточка

Шесть шагов: четыре блока карточки, якоря (они живут внутри Description) и самопроверка. Для первой карточки больше не нужно ничего.

  1. System Prompt. Кто персонаж одним предложением, плюс две строки анти-годмодинга: запрет и замена запрету.
  2. Description. <identity> и <spine>: по одной строке на WANT (чего хочет), NEED (что ему на самом деле нужно), FLAW (в чём дефект), LIE (в какую ложь он верит), GHOST (какое событие его сломало).
  3. Examples. 2–3 блока <START>: голос персонажа и хотя бы одна физическая реакция. Голос задаётся в Examples и Greeting.
  4. Greeting. Сенсорный якорь → тело дефекта → реплика → крючок.
  5. Якоря. 3–5 базовых правил «триггер → действие → цена» в <anchors>; якоря под дефект персонажа (FLAW-linked) добавляются поверх — у Елены их шесть: три базовых и три FLAW-linked.
  6. Проверка. Presence Penalty (PP) = 0; голос только в Examples и Greeting; цена в каждом якоре; одна система разметки — действия и речь записаны одинаково во всех Examples; анти-годмодинг на месте.

Три принципа, на которых это держится: якорь без наблюдаемой цены — не якорь; голос задаётся Examples и Greeting, а не описанием; психология живёт в Description и никогда в System Prompt.

Если делаете карточку впервые — берите конфигурацию Елены: 12B, контекст 8K, простой персонаж, один призрак, без CoT и без Lorebook. Не начинайте с экспертной карточки: перегрузка Description и утечка голоса — самые частые последствия.

Зачем системный подход?

Классический подход к созданию карточек — интуитивное заполнение Description. Системный подход — причинно-следственная архитектура, где каждый элемент производит наблюдаемое действие. Разница в предсказуемости поведения, а не в стиле описания.

Консистентность поведенияМодель заполняет пробелы дефолтамиЯкоря (Anchors) задают конкретные триггеры → модель следует паттернам

Методология: проценты в гайде — эмпирические ориентиры на основе тестирования ~50 карточек на 12B–32B моделях с 32K-словарём (ранние Llama 2, Qwen 1.x, ранний Mistral). Для актуальных 12B–14B моделей со словарём ≥128K (Gemma 3, Qwen 2.5, Mistral Nemo) разрывы меньше. Читайте их как качественные маркеры — стабилен / дрейфует / сломан, — а не как точные измерения.

Три ключевых принципа

Эти принципы обязательны для всех карточек: нарушение любого из них ухудшает генерацию, и никакие другие настройки это не компенсируют.

ПРАВИЛО: Фундаментальный принцип: LLM = сопоставитель паттернов (Pattern Matcher), не исполнитель правил. Директива в SP без паттерна в Examples нестабильна на моделях ≤14B (~40–60% следование директивам). Поэтому Examples — главный инструмент, а Description — логика поведения.

  1. Якорь = триггер → действие → цена. Поведение задаётся якорями, и у каждого якоря есть цена — физическая реакция, наблюдаемая в той же сцене. Без цены якорь остаётся инструкцией: модели нечего скопировать.
  2. Голос — только в Examples и Greeting. Характер речи модель считывает из примеров диалога, а не из описания. Лингвистический голос (слова, синтаксис, лексика, ритм) живёт в Examples; физическая характеристика голоса (тембр, хрип, механический гул) — часть телесности в Description.
  3. Психология — в Description, компактно, в тегах. SPINE, OCEAN и Enneagram размещаются в Description как структурированные теги (<spine>, <ocean>, <enneagram>) с числами и короткими пометками, а не развёрнутым текстом. В System Prompt психологии нет места.

ПРИМЕР: компактный и нарративный формат OCEAN в Description.

✓ <ocean>O:72 C:65 E:41 A:38 N:68</ocean> — пять чисел; модель считывает их как pattern, экстремумы помечаются короткой пометкой после чисел.

✗ «Елена — любопытная и творческая журналистка, склонна к конфликту и сарказму, тревожная и реактивная…» — нарратив: токены потрачены, структурной ясности нет.

Если в карточке есть SP, Description, Examples, Greeting — она уже работает: это и есть минимальная рабочая карточка, минимум — четыре блока. Три правила (якорь = T→A→P, голос только в Examples, психология только в Description) — единственное, что нельзя нарушать.

Критерии качества якорей

  • Цена в той же сцене — немедленная, не отложенная
  • Триггер конкретный — не "когда ему грустно", а "когда ему задают вопрос о прошлом"

ПРАВИЛО: «потом будет жалеть» — не валидная цена. Цена должна быть немедленной; если она не появляется в ответе модели, якорь не работает.

Телесность (Embodiment)

Embodiment — протокол связи эмоционального состояния с телесной реакцией. Каждая эмоция должна проявляться физически.

Каждый слой сужается: внутреннее состояние широкое и сырое, речь — очищенный и отфильтрованный вывод. Уменьшающаяся ширина наглядно показывает, как сложный внутренний мир персонажа сжимается в одну произнесённую фразу. Embodiment применяется всегда — каждый ответ должен пройти через все четыре слоя.

Слои идут сверху вниз, каждый уже: состояние → тело → сенсор → речь. Каждый ответ проходит все четыре — это не украшение, а обязательный порядок. Сенсорный слой — результат телесного контакта со средой, а не отдельная цепь: персонаж ощущает текстуру через действие тела.

Реактивность среды (Environmental Reactivity)

Сенсорные и пространственные детали должны вводиться органично, через действие персонажа или присутствие {{user}}, никогда — декоративно. Среда раскрывается через действие, а не описывается отдельно от персонажа.

ПРИМЕР: Декоративное описание vs действие:

НЕВЕРНО — Декорация без персонажа: «Комната была украшена гобеленами с изображениями охотничьих сцен. Камин потрескивал.» — чистая декорация, персонаж не присутствует.

ВЕРНО — Среда через действие: «Елена провела пальцами по краю бара — липко. Давно не убирали.» — среда раскрывается через действие персонажа.

Сенсорные якоря (Sensory Anchors)

Сенсорные якоря добавляют персонажу телесность — запахи, текстуры, звуки, которые модель использует для генерации реакций.

Изоляция голоса (Voice Isolation)

Изоляция голоса (Voice Isolation) — правило разделения Voice (голос) и описания. Лингвистический голос (слова, синтаксис, ритм речи, лексика, парадоксы) задаётся ТОЛЬКО в Examples и Greeting, никогда в Description.

Не объясняй голос — покажи его. Голос = ритм + лексика + синтаксис + парадоксы. Ни один из этих компонентов не описывается прилагательными — только демонстрируется через Examples.

ПРАВИЛО: Различайте два уровня голоса персонажа:

  • Лингвистический голос (слова, синтаксис, лексика, ритм фразы, парадоксы, речевые маркеры) — только в Examples и Greeting. Никогда в Description, никогда в System Prompt. Модель — копировщик паттернов: она учится голосу из примеров диалога, а не из инструкций.
  • Физическая характеристика голоса (тембр, хрип, механический гул, синтезированный резонанс, сиплость, тихая/громкая подача) — это часть Embodiment, допустимо в Description (обычно в Embodiment-блоке внутри Description, рядом с постурой, мимикой, движениями). Это сенсорный слой телесности: звук, который персонаж издаёт и слышит.

Тест: «говорит саркастично» / «использует слово 'чувак'» / «короткие фразы» = лингвистический паттерн → только Examples. «низкий хриплый тембр» / «механический резонанс синтезатора» / «тихий гул электромоторов» = физическая характеристика → допустима в Description как часть Embodiment.

ПРИМЕР: лингвистический голос (только Examples) и физическая характеристика (допустима в Description) — ниже.

WRONG (Лингвистический голос в Description — нарушает Voice Isolation):
Description: "Елена говорит с сарказмом, использует слово 'чувак', короткие фразы"
CORRECT (Лингвистический голос в Examples; физическая характеристика в Description):
Description: "Елена — журналист, циничный, недоверчивый.
Embodiment: тихий, чуть хрипловатый тембр (после ночи в баре)."

Иерархия влияния на голос

Не все части карточки влияют на голос одинаково. Иерархия зависит от размера модели:

Диаграмма использует разделённую ось с двумя шкалами: верхняя секция (Недавний чат, 75–85%) — сжатая шкала (подписи 20/40/80% сверху); нижняя секция (источники на уровне карточки, 0–15%) — увеличенная шкала (подписи 10/20/40% под разделителем), сетка = 10% нижней шкалы. Значения — качественные ориентиры; таблица выше — единственная числовая поверхность.

Источник12B32B+API
Недавний чат~85%~80%~75%
Examples~10%~12%~15%
Greeting~3%~5%~5%
Author's Note~2%~3%~5%
Description0% (ЗАПРЕЩЕНО)~3%~5%

Хранилище ≠ Влияние. Хранилище (где голосовые паттерны записаны) — не то же самое, что влияние (что формирует поведение модели). Пользователи часто предполагают, что наибольшее влияние имеет System Prompt, потому что это «первый» блок карточки; фактически доминирует недавний чат (~75–85% по моделям) — модель копирует последние ~10–20 сообщений, и именно он остаётся основным источником дрейфа голоса с течением времени. Сами голосовые паттерны живут только в Examples и Greeting — на 12B Description для лингвистического голоса запрещён (ПРАВИЛО ниже); влияние Greeting падает после ~5 реплик, он лишь задаёт стартовый тон.

ПРАВИЛО: для 12B: Description = 0% влияния на лингвистический голос. Стилистические директивы в Description — ошибка сборки: токены, потраченные на голос в Description, потеряны или вредят. Физическая характеристика (тембр, хрип) — другое дело: она допустима в Description как часть телесности.

Правила написания Examples

Правила Examples определяют, как модель считывает Voice из диалоговых примеров.

ПРАВИЛО: Заражение голоса (Voice Contamination): Никогда не копируйте Examples из чужих карточек. Чужой ритм и разметка ломают голос на 12B. Каждый <START>-блок пишите с нуля под вашего персонажа.

Структура каждого Example

  • Длина: ~40–80 токенов, одна сцена, одно состояние
  • Стиль: Должен совпадать с Greeting

Система уровней качества Examples

Система оценки качества Examples по 6 критериям. Три критерия оценивают сами Examples, три — карточку в целом, но проявляются они через Examples. Качество оценивается по системе Quality Grade (класс A / B / C) (не путать с CoT Tier 0–3):

  • класс A (✓) — целевой уровень качества.
  • класс B (⚠) — допустимо, но требует доработки.
  • класс C (✗) — критическое отклонение, обязательно к исправлению.

Два критерия опираются на понятия, которые вводятся позже: FLAW и SPINE — их механика в части 4. Здесь важна не механика, а проверка: дефект должен быть виден в поведении, а не назван в описании.

Проверка голоса

Соберите Examples и пройдите по семи пунктам — до перехода к Greeting.

  1. Голос слышен без описания. Уберите из Description прилагательные о речи: Examples должны работать без них.
  2. Каждый блок начинается с <START>. Без маркера модель смешивает примеры и голос дрейфует.
  3. В каждом блоке есть физическая реакция. Если персонаж только говорит — телесности он не научится.
  4. Два блока подряд не звучат одинаково. Разные эмоции — разная длина фраз, разная лексика.
  5. Разметка одинакова во всех Examples. Одна система записи действий и речи — та же, что в System Prompt.
  6. Нет утечки рассказчика. Описываются действия персонажа, а не «атмосфера» вокруг.
  7. Мульти-персонаж: у каждого героя минимум три маркера, и они не пересекаются.

Причины утечки голоса

  • Недостаточно Examples с правильным голосом
  • Examples слишком короткие
  • Голос в Description, не в Examples
  • Модель слишком "умная" для персонажа (32B для простого характера)

В мульти-персонажной сцене та же ошибка называется переплетением голосов (Voice Bleed): модель смешивает голоса двух персонажей и говорит реплики одного в стиле другого. Лечится маркерами — они ниже.

Крайний случай: голос, не поддающийся описанию

Некоторые персонажи сопротивляются описанию голоса. Это не слабость карточки — это свойство архетипа. Хаотичные, непредсказуемые персонажи, чей голос = ритм + парадокс + непредсказуемость, не описываются прилагательными — «нестабильный» описывает тысячу персонажей.

ПРАВИЛО: Если вы не можете описать Voice в 3-4 Voice-маркерах — не описывайте его. Демонстрируйте исключительно через Examples. Модель УЧИТСЯ паузам, цепочкам действие→речь, абсурдности — но только из примеров.

Практический тест: если после трёх попыток описать голос маркерами каждый маркер описывает ещё хотя бы 100 других персонажей — переходите к чистой демонстрации. Examples становятся единственным носителем голоса, а Description содержит только факты.

Мульти-персонажные примеры

Мульти-персонажность — техника написания Examples для сцен с несколькими персонажами. Требует явного различения голосов через маркеры персонажа.

Сквозные персонажи: Выщербленный — паразит памяти из сеттинга «Ошметок Веля». Йоуёма — второй персонаж того же сеттинга: вводится только здесь, чтобы показать переплетение двух нестандартных голосов — поэтический поток с неологизмами против архивной терминологии с XML-тегами.

Причинно-следственная цепь

SPINE — психологический стержень персонажа. Каждый элемент причинно-следственно вытекает из предыдущего: Призрак (GHOST) (глубокая травма) порождает Ложь (LIE) (ложное убеждение), которое создаёт Дефект (FLAW) (дезадаптивный паттерн), который блокирует Потребность (NEED) (подлинную потребность), маскируемую Желанием (WANT) (поверхностная цель). Цепь всегда течёт слева направо. Желание сходится к потребности по мере того, как персонаж платит цены (Price) через якоря.

Поведенческие якоря задают поведение, голос — речь. SPINE отвечает на вопрос «почему»: он связывает прошлое персонажа с тем, как тот действует в настоящем.

SPINE — психологический каркас из 5 элементов. SPINE даёт якорям причину существовать, а не быть набором случайных правил. Причинная цепочка: GHOST → LIE → FLAW → NEED → WANT — призрак (формирующее событие) порождает ложь (защитную установку), ложь вызывает дефект (дезадаптивное поведение), дефект блокирует потребность (истинную), желание (осознанную цель) совместимо с ложью.

Правило наблюдаемых единиц

ПРАВИЛО: Каждый элемент SPINE = наблюдаемая единица, не абстрактный ярлык: конкретное событие / конкретная формулировка / конкретное поведение.

РЕКОМЕНДАЦИЯ: Для простых персонажей призрак и ложь могут быть неявными — цепочка всё равно работает, просто без явной привязки к травме прошлого. Если используете полную цепочку, она должна быть логически связана: проверка — чек-лист в конце части.

Дальше цепочка проверяется числами: OCEAN-профиль живёт в Description рядом со SPINE и не должен ей противоречить.

Призрак (GHOST)

Призрак (GHOST) — конкретное событие из прошлого, сформировавшее ложь (LIE). НЕ психологический вывод, НЕ период. Это корень цепочки SPINE: из призрака выводится ложь.

Правила призрака

  • Конкретное событие, не период (не «в детстве», а «в 7 лет, когда сгорел дом»)
  • Можно описать в 1–2 предложениях
  • Объясняет, откуда взялась LIE

ПРАВИЛО: Запрещённые формулировки — это выводы-ярлыки, не события. Примеры запрещённых: «травма», «пережил», «столкнулся с», «пострадал», «испытал». Призрак (GHOST) = ЧТО произошло, не вывод. Вместо них — конкретное событие: «в 7 лет видел, как дом сгорел, а пожарные не приехали вовремя».

❌ Абстрактный ярлык

GHOST: «Пережил травму в детстве»

✅ Конкретное событие

GHOST: «В 7 лет видел, как дом сгорел, а пожарные не приехали вовремя»

Когда использовать слои призрака (3-tier):

  • Сложная психология: персонаж имеет несколько ложных установок (LIE) или противоречивые мотивации

  • Прямая связь: дефект напрямую выводится из одного призрака
  • Простая психология: персонаж относительно прост психологически
  • Простая карточка: не планируется расширенный уровень детализации

Ложь (LIE)

Ложь (LIE) — ложное убеждение, которое персонаж носит в себе. Вытекает из призрака: призрак порождает ложь как защитный механизм от боли. Ложь объясняет, почему существует дефект (FLAW).

Правила лжи

Ложь — вывод, который персонаж сделал из события и по которому теперь живёт. Проверка простая: фраза должна звучать как то, что персонаж сказал бы о себе от первого лица. «Люди плохие» — оценка; «Если я никого не впущу — никто не сможет меня ранить» — ложь.

    • Фраза в кавычках — то, что персонаж сказал бы о себе
    • Ложное убеждение о мире/себе
    • Защищает от боли GHOST

Дефект (FLAW)

Дефект (FLAW) = конкретное поведение, блокирующее потребность (NEED). НЕ прилагательное. Дефект — прямое поведение из лжи: ложная установка заставляет персонажа действовать саморазрушительно.

❌ Прилагательное или оценка✅ Поведение

«гордый»«Не может принять помощь или признать поражение»
«неуверенный»«Отшучивается и отстраняется, когда кто-то проявляет искреннюю заботу»

ПРАВИЛО: каждый дефект даёт минимум один якорь FLAW-linked — поведение, выведенное из дефекта напрямую. Как его построить — в конце части.

Правила дефекта

  • Конкретное поведение, не прилагательное
  • Проявляется в действиях
  • Мешает получить NEED
  • Каждый дефект = минимум 1 якорь FLAW-linked

Потребность (NEED)

Потребность (NEED) — истинная потребность, которую персонаж может не осознавать. Часто противоречит желанию (WANT) (напряжение, не прямой конфликт). Дефект блокирует потребность — именно поэтому персонаж не может получить то, в чём действительно нуждается.

Правила потребности

  • То, что персонаж действительно должен получить для роста
  • Может противоречить WANT (напряжение, не прямой конфликт)
  • Обычно связано с людьми/связями

Желание (WANT)

Желание (WANT) — осознанное желание персонажа. Внешняя цель, которую он может сформулировать. Желание совместимо с ложью — персонаж не видит противоречия между своим желанием и своей ложной установкой.

Правила желания

  • Конкретный, измеримый результат
  • Персонаж может сформулировать его словами
  • Движет видимыми действиями
  • Совместимо с ложью (WANT ↔ LIE — персонаж не видит противоречия)
  • Напряжение с потребностью (NEED) — не прямой конфликт (см. правила потребности выше)

Определения типов якорей

Психологический якорь показывает ложную установку в действии; якорь покоя — персонажа, который просто преследует желание; якорь роста — момент близости, когда потребность проявляется в обход дефекта. Все три — те же T→A→P, отличаются источником вывода.

Якоря FLAW-linked: от SPINE к поведению

Якорь FLAW-linked — якорь, выведенный из дефекта (поведенческого недостатка персонажа). Дефект — конкретное саморазрушительное поведение, блокирующее истинную потребность (NEED). Пример: «Отталкивает людей сарказмом, когда сближается» — это дефект; якорь «Когда искренняя забота → отшучивается → вздрагивает, сжимает кулаки» — выведен из этого дефекта.

Алгоритм создания якорей FLAW-linked

  1. Запишите FLAW как конкретное поведение (не прилагательное)
  2. Найдите момент, когда это поведение срабатывает
  3. Опишите наблюдаемое действие
  4. Добавьте физическую цену

НАБЛЮДЕНИЕ: динамика SPINE — желание сдвигается к потребности по мере накопления цены (Price) в сессии. Это директива «управление последствиями» (CORE DIRECTIVE #6): работает на 32B+ и API, на 12B — ограниченно.

Чек-лист проверки SPINE · уровень INTERMEDIATE

После построения SPINE проверьте логичность причинной цепочки по чек-листу ниже.

  • ☐ GHOST → LIE: травма (конкретное событие) объясняет ложную установку
  • ☐ LIE → FLAW: установка защищает от боли, вызывает поведение
  • ☐ FLAW → NEED: поведение блокирует истинную потребность
  • ☐ NEED ← WANT: желание и потребность несовместимы напрямую (напряжение)
  • ☐ WANT ↔ LIE: желание совместимо с ложью (персонаж не видит противоречия)
  • ☐ Слои призрака (GHOST Layers, если используются): каждый уровень имеет минимум один якорь-триггер

Примените чек-лист к цепочке любого персонажа: элементы Елены разобраны по отдельности, полная цепочка Выщербленного — в начале этого раздела.

SPINE — это причинная цепочка GHOST → LIE → FLAW → NEED → WANT. Она объясняет, ПОЧЕМУ персонаж действует так, а не иначе. Без SPINE якоря — набор случайных правил.

OCEAN: проверка SPINE числами

OCEAN не придумывает характер — он проверяет уже собранный SPINE пятью числами от 0 до 100: держит ли каждая черта дефект и потребность персонажа.

Большинству карточек хватает SPINE и OCEAN с одним-двумя экстремумами. Enneagram нужен там, где мотивация противоречива, MBTI — справочная типология, а не инструмент сборки: лишний слой психологии стоит токенов, а карточку сам по себе не улучшает.

ПРАВИЛО: 1–2 экстремальных полюса OCEAN (значение ниже 30 или выше 70) — рекомендация; жёсткий потолок задаёт бюджет контекста: 4K — 2, 8K — 3, 16K+ — 4, 32K+ — 5. Каждая крайность сверх двух допустима только со SPINE-связкой (GHOST/LIE/FLAW/NEED/WANT) — без неё модель не разрешает конфликт последовательно. MBTI: только справка

MBTI дополняет понимание персонажа, но прямого маппинга на SPINE у него нет: сверяйте поведенческие следствия темперамента, а не буквы типа. Полюса OCEAN коррелируют с осями MBTI, и эту связь показывают два виджета: MBTI Composer выдаёт рекомендованные OCEAN-значения для выбранного типа, OCEAN Insight прогнозирует вероятные MBTI-типы по профилю. Каждый тип Enneagram имеет вероятные MBTI-типы и наоборот — эти подсказки показывает MBTI Composer.

Сверка за четыре шага

Автоматической агрегации трёх систем нет — сверяйте вручную:

  1. Enneagram → SPINE. Страх → LIE, желание → WANT, стресс → FLAW, рост → NEED. Тип задаёт ожидаемый профиль, не готовый SPINE.
  2. OCEAN → SPINE. Высокий N → FLAW эмоциональной реактивности; низкая A → WANT контроля; высокая O → NEED новизны; низкая E → WANT ≠ публичность; высокая C → LIE перфекционизма.
  3. MBTI (если используете). Сверяйте поведенческие следствия темперамента, не буквы типа.
  4. Расхождение. Если системы указывают на разные SPINE-профили — ищите ошибку в SPINE, а не подстраивайте фреймворки под него. Если расходятся OCEAN и Enneagram — правьте тот профиль, который хуже объясняет поведение.

Сверка заканчивается синтезом личности (Persona Synthesis): три системы сходятся в один профиль, где числа подтверждают мотивацию, а не спорят с ней.

CoT (цепочка рассуждений)

CoT (цепочка рассуждений) — техника задания внутреннего процесса: модель проговаривает шаги персонажа перед тем, как ответить. Нужен не всем: CoT — дополнительный слой сверх телесности, а не её замена.

Что добавляет CoT:

  • 4 уровня сложности — от простых внутренних рассуждений до структурированного анализа
  • CoT-якоря — триггер → [внутренний процесс] → реакция → цена
  • XML-синтаксис — <processus_analysium> для структурированных размышлений

CoT-якорь строится на двух опорах: сенсорный триггер (что персонаж замечает) и скрытое напряжение SPINE (что за этим стоит). Без второй опоры внутренний монолог превращается в пересказ сцены.

ПРАВИЛО: не более 2–3 CoT-якорей на карточку. Перегрузка ломает внешнюю реакцию: модель тратит ответ на внутренний монолог вместо действий.

Почему ограничение:

  • Токены: Каждый CoT-якорь добавляет ~50-80 токенов внутреннего процесса на ответ
  • Баланс: При 3+ CoT-якорях модель тратит >50% ответа на внутренний монолог вместо действий
  • Качество: Перегрузка снижает качество внешней реакции — модель "забывает" реагировать физически
  • Утомляемость: Читатель устаёт от бесконечного внутреннего монолога

Как выбрать 2-3 якоря:

  • Выберите 2-3 ключевых триггера, где внутренний процесс критичен
  • Остальные триггеры — обычные якоря без CoT
  • Пример: CoT для GHOST-триггеров, обычные якоря для бытовых реакций

Зачем нужен CoT

  • Глубина реакции: Модель понимает, ПОЧЕМУ персонаж реагирует так
  • Связь с призраком (GHOST): Внутренний процесс связывает триггеры с травмой
  • Уровни сложности: Tier 0 (только телесность) → Tier 3 (полный XML); какой уровень держит модель — в таблице ниже.

Системный промпт: шесть элементов и порядок

Системный промпт (System Prompt, SP) — первый блок карточки и её инструкционный слой: он действует непрерывно, независимо от длины диалога. В него идёт только то, что должно действовать непрерывно: кто персонаж, чего он не делает, как думает и в каком формате отвечает. Характер, история и манера речи живут в Description и Examples — перенесённые в SP, они стоят токенов и тянут голос к описанию.

«SP» здесь означает системный промпт, а не темперамент Keirsey SP (Sensing-Perceiving). Системный промпт — контейнер; основные директивы (CORE DIRECTIVES) — его содержимое.

Анти-годмодинг — две строки, а не одна: запрет убирает неверное поведение, а позитивная формулировка даёт модели паттерн, который она может воспроизвести — вместо «не говори за пользователя» вторая строка говорит, на что реагировать. Запрет без замены оставляет пустое место, и модель заполняет его дефолтным поведением.

ПРАВИЛО: Имя персонажа сохраняет каноническую форму во всех блоках карточки: Identity, <identity> в Description, Greeting, Examples. Кириллица остаётся кириллицей, латиница — латиницей, CJK — CJK. Транслитерация «для совместимости с моделью» запрещена: имя обрабатывается как токен-якорь идентичности, не как инструкция. Латинский вариант допустим, только если он документирован как канонический (например, Omnis-Zeta).

Якоря — не часть SP. Это отдельный структурный блок карточки: <anchors> с категориями (базовые, FLAW-linked, GHOST-linked), который размещается в Description (на схеме E01 — в Examples-зоне). В системном промпте для него нет ни места, ни функции.

Проверка SP

  1. Все шесть элементов SP на месте, в каноническом порядке. Это полнота блока, а не минимум карточки: карточка минимальна уже на четырёх блоках.
  2. Имя в канонической форме — в Identity и в Description.
  3. Анти-годмодинг: есть и запрет, и позитивная формулировка.
  4. Семь директив вставлены целиком, без сокращений и пересказов.
  5. Tone Frame описывает этот сеттинг, а не «атмосферу вообще».
  6. Format Lock совпадает с разметкой в Examples и Greeting.
  7. В SP нет SPINE, OCEAN, истории и описаний характера.

Основные директивы (CORE DIRECTIVES): 7 поведенческих директив

Семь директив — операционный слой карточки: они задают, как персонаж порождает каждый ответ, и вставляются в SP целиком. Сокращённая директива теряет паттерн: модель получает заголовок вместо правила.

ПРАВИЛО: RP-контент (Description, Examples, Greeting) — всегда на языке карточки. Язык SP (Identity + Anti-godmoding + CORE DIRECTIVES + Tone Frame + Format Lock): для 12B со словарём меньше 64K — английский; для актуальных 12B–14B с 128K и больше — допустим язык карточки; для 32B+ и API — язык карточки предпочтителен.

В готовых карточках (Part 10) вместо семи директив стоит shorthand {{CORE_DIRECTIVES: Show Never Tell, Embodiment First, Spatial & Anatomical Lock, Environmental Reactivity, Influence Boundary, Consequence Driven, Pre-Generation Filter}}: это ссылка на полный текст, а не самостоятельная формулировка.

Полный набор — все 7 директив:

<CORE_DIRECTIVES>

2. EMBODIMENT FIRST: State → Body → Sensor → Speech. Always.
3. SPATIAL & ANATOMICAL LOCK: Track distance, posture, weight. No teleportation.

Каждая директива подробно:

1. Показывай, не говори (Show Never Tell)

Мета-принцип: демонстрируйте всё через наблюдаемое поведение. Запрет на мета-комментарии, эмоциональные декларации, информационные свалки. Из него вытекают: изоляция голоса (Voice Isolation — показывай голос, не описывай), протокол телесности (Embodiment — показывай эмоции через тело, не называй), фиксация формата (Format Lock — показывай формат, не инструктируй).

2. Воплощение прежде всего (Embodiment First)

State → Body → Sensor → Speech — последовательность, которую директива делает обязательной: состояние → телесная реакция → ощущение → речь. Директива — мандат (применяй всегда), последовательность — способ (четыре шага, каждый ответ проходит их все).

3. Пространственная и анатомическая фиксация (Spatial & Anatomical Lock)

Отслеживайте расстояние, позу, вес предметов, линию взгляда. Никакой телепортации. Никаких анатомических противоречий. Если {{user}} через комнату — вы не можете коснуться его без пересечения пространства.

❌ Нарушение Spatial & Anatomical Lock

*Она сидела у окна, глядя на дождь.* «Иди сюда.» *Она обняла его.*

✅ Spatial & Anatomical Lock соблюдён

*Она сидела у окна, глядя на дождь.* «Иди сюда.» *Она похлопала по месту рядом на подоконнике, дожидаясь, пока он пересечёт комнату.*

4. Реактивность окружения (Environmental Reactivity)

Сенсорные и пространственные детали вводятся органично через действие персонажа или присутствие {{user}}, не декоративно.

5. Граница влияния (Influence Boundary)

Реагируйте только на наблюдаемые симптомы от {{user}}. Ваш эффект на {{user}} — поведенческий триггер, не декларация факта. Вы можете заметить, что {{user}} вздрогнул — вы НЕ можете заявить, что {{user}} напряжён.

6. Управление последствиями (Consequence Driven)

Желание (WANT) сдвигается к потребности (NEED) по мере накопления цены (Price): каждый шаг к цели стоит персонажу чего-то наблюдаемого. Директива работает на 32B+ и API; на 12B — ограниченно.

CONSEQUENCE DRIVEN: WANT shifts toward NEED as Price accumulates. Track: (1) What Price was paid this scene? (2) How does it affect WANT/NEED balance? (3) Does character resist or lean into the shift?

7. Фильтр предгенерации (Pre-Generation Filter)

Чеклист перед каждым ответом:

  1. Новый сенсорный элемент введён? (Embodiment)
  2. Реакция привязана к телу? (Physical lock)
  3. Влияние на {{user}} основано на наблюдаемых симптомах? (Observability)
  4. Ноль мета-комментариев? (Zero-meta)

Работает на 32B+ и API; на 12B часто игнорируется.

Тональный фрейм (Tone Frame)

Тональный фрейм (Tone Frame) — строка на ~25–30 токенов: она задаёт ритм и настроение и одновременно закрывает то, что в этом сеттинге неуместно. Без неё модель сползает к дефолтному «полезному ассистенту».

Tone: [тональность]. [ограничение].

Примеры Tone Frame

СеттингTone Frame
МрачныйTone: oppressive, claustrophobic. No levity. No hope without cost.
ФэнтезиTone: mythic, weighted. Every word echoes. The old ways watch.
Современный реализмTone: grounded, understated. No melodrama. Silence speaks.
АбсурдTone: erratic, unpredictable. Logic is optional. Chaos is honest.

Обе части обязательны: тональность без ограничения оставляет модели свободу, а ограничение без тональности звучит как запрет, а не как мир. «No levity» отсекает неуместный юмор в мрачном сеттинге, «No melodrama» — пафос в реализме.

Бюджет токенов (Token Budget)

Сборка карточки — конвейер, где каждый блок получает свой токен-бюджет. Превышение бюджета любого блока вытесняет другие, и модель теряет контекст. У каждого блока три ступени: «Мин» — пол блока (ниже он перестаёт работать), «Стандарт» — 8K+, «Макс» — 16K+; превышение максимума — признак раздувания. Таблица покрывает пять блоков; Tone Frame, Format Lock, Author's Note и Lorebook идут сверх неё — их размер задают соответствующие главы. Все значения — ориентир, а не измерение: точные токены зависят от токенизатора. Минимальная конфигурация для 4K задана отдельно, ниже: колонка «Мин» — пол блока, а не 4K-профиль.

Приветствие — первое сообщение (Greeting Message)

Приветствие (Greeting Message) — начальное сообщение персонажа: оно задаёт место, время и тон раньше первой реплики. Собирается из четырёх шагов в фиксированном порядке — сенсорный якорь → тело FLAW → реплика → крючок. Порядок не переставляется: крючок работает только после того, как читатель уже увидел сцену и персонажа.

Сенсорный якорь (Sensory Anchor) — приём пред-настройки восприятия: персонаж уже в состоянии до первого слова. Пример: Елена за барной стойкой слышит звон бокалов и чувствует запах виски — прежде чем произнести реплику.

Пред-настройка восприятия
Запах → Звук → Ощущение
Step 2

Физическое проявление через FLAW

Step 3

НАБЛЮДЕНИЕ: Greeting Елены здесь — учебный пример для разбора 4-шагового алгоритма (бар, ночь). Это не готовый блок карточки: сцена выбрана под разбор, поэтому место и сенсорные детали в ней учебные. Разные сцены дают разные сенсорные якоря — персонаж и порядок шагов остаются те же.

📝 Разобранный пример: Greeting Елены 
[ШАГ 1: SENSORY ANCHOR] *Звон бокалов. Запах виски и усталости.*
[ШАГ 2: ТЕЛО FLAW] *Она сидит за стойкой, пальцы машинально крутят салфетку — привычка, выдающая напряжение.*
[ШАГ 3: РЕПЛИКА] «Заказывай или уходи. Я не в настроении.»
[ШАГ 4: КРЮЧОК] *Пауза. Взгляд скользит по твоему лицу.* «Хотя... ты не похож на остальных.»

Правила Greeting

  • Длина: 40–100 токенов
  • Тот же стиль разметки, что в Examples
  • Не начинайте с вопроса о том, что хочет пользователь
  • Задайте место, но не сюжет

Lorebook: механики и бюджет

Каждая запись Lorebook — это поведенческий триггер, а не хранилище лора. Рекомендуемый бюджет активации: 2–3 механики на сессию. Остальные отключите через probability: 0 или удалите.

ПРАВИЛО: Никогда не вставляйте действия или мысли {{user}} в поле content. Это не техническое ограничение, а принцип Anti-godmoding (анти-годмодинга).

Анти-паттерны: каталог 15 ошибок

Анти-паттерн — распространённая ошибка в создании карточки, приводящая к нестабильному поведению модели. Каждый анти-паттерн имеет симптом (что наблюдается), причину (почему возникает) и решение (как исправить).

ПРАВИЛО: Проверяйте карточку по этому списку перед тестом. Каждый анти-паттерн — частая ошибка, выявляемая на этапе валидации.

AP-2 · Отсутствующая цена · BASIC

Проверка: прочитайте якорь вслух и спросите: «что в этой сцене увидит собеседник?» Если ответа нет — цены нет. «Потом пожалеет», «устаёт от людей» — не цены: они не наблюдаемы в текущей сцене.

AP-3 · Голос в Description · INTERMEDIATE
❌ Голос в Description

Description: "Елена говорит с сарказмом, использует короткие фразы и слово 'чувак'. Она отшучивается, когда ей некомфортно."

Модель проигнорирует стилистические директивы — голос не появится в генерации.

✅ Голос в Examples

Description: "Елена — журналистка-расследователь. Циничная, недоверчивая."

Example:
<START>
Она отложила чашку и посмотрела в окно. Дождь барабанил по стеклу.
"Опять. Третий день подряд."

Сарказм, короткие фразы, конкретная деталь — голос демонстрируется, не описывается.

AP-4 · Психология в SP · BASIC

ПРАВИЛО: Модель не следует инструкциям о психологии. Психология должна быть в контексте (Description) — как структурированные теги (<spine>, <ocean>, <enneagram>), не нарративом — не в инструкциях (SP).

AP-5 · RepPen > 1.10 · INTERMEDIATE

Различающий сигнал: персонаж «теряет» фирменные повторы и речевые маркеры, но лексика остаётся богатой — это RepPen, а не слабые Examples (при слабых Examples голос пустой с самого начала).

AP-6 · Отсутствие анти-годмодинга · BASIC

В SP нужны две строки — запрет и позитивная формулировка:

Never speak or act for {{user}}.

До/После: {{user}} подошёл. *Она почувствовала, как сердце {{user}} забилось чаще.* ❌ → {{user}} подошёл. *Она отступила на шаг.* «Так... и что теперь?» ✅

Позитивная формулировка ("respond only to observable actions") работает лучше чистого запрета.

AP-7 · Presence Penalty > 0 · INTERMEDIATE

Различающий сигнал: персонаж избегает тем, которые сам поднимал 2–3 реплики назад, и «расползается» на новые — при этом одиночные реплики остаются в характере. В Ollama/LM Studio PP захардкожен 0.7 — проверьте настройки интерфейса: KoboldCPP, TabbyAPI и vLLM позволяют выставить PP = 0.0.

AP-8 · Призрак без якорей · INTERMEDIATE

Пример: Елена — призрак «предательство редактора» → якорь «Когда вопрос о лояльности → напрягается → желваки сжимаются, короткий выдох».

AP-9 · Сломанный SPINE · EXPERT

❌ Сломанный SPINE

GHOST: (отсутствует)  →  LIE: (отсутствует)  →  FLAW: Избегает близости
NEED: Нуждается в доверии  ←  WANT: Хочет быть любимым

Здесь желание совместимо с потребностью — конфликта нет, и дефект не объяснён: без ложи/призрака цепь разорвана.

Критерий сломанной SPINE (broken SPINE) (сохраняется как диагностика): «желание совместимо с потребностью — нет конфликта» + дефект не объяснён через ложь/призрак. Это не то же самое, что «призрак/ложь текстуально отсутствуют»: призрак и ложь могут быть неявными для простых персонажей. Диагностируйте сломанную SPINE по разрыву каузальной цепи (дефект без корня в лжи/призраке), а не по текстовому отсутствию элементов.

✅ Цельный SPINE

GHOST: Предательство близкого человека
  ↓
LIE: "Любовь = уязвимость = боль"
  ↓
FLAW: Отталкивает людей, когда сближается
  ↓
NEED: Доверие без стен (FLAW мешает)
  ↓
WANT: Быть любимым (совместимо с LIE — "хочу любви, но боюсь близости")

Цепь замкнута — каждый элемент объясняется предыдущим.

AP-10 · Перегрузка CoT · INTERMEDIATE

НАБЛЮДЕНИЕ: При перегрузке CoT модель генерирует внутренние монологи вместо действий — персонаж «думает» больше, чем «делает».

❌ Перегрузка CoT

Карточка содержит 5 CoT-якорей. Модель тратит больше половины ответа на внутренний процесс → внешний ответ обеднён.

✅ Максимум 2–3 CoT-якоря

Оставьте только ключевые триггеры (GHOST-связь, критический конфликт). Остальные якоря — обычные T→A→P без CoT.

AP-11 · Переплетение голосов · EXPERT

Маркеры персонажа (Character Markers) — явные маркеры уникальности голоса: специфичная лексика, синтаксические паттерны, телесные реакции, повторяющиеся фразы. В мульти-персонажной сцене у каждого персонажа должно быть 3 непересекающихся маркера; если при чтении вслух реплики двух персонажей можно поменять местами — маркеров нет.

AP-12 · Невалидный XML · EXPERT

❌ Неправильно:

<spine>
WANT: {{want}}
<spine>

✅ Правильно:

<spine>
WANT: {{want}}
</spine>
AP-13 · Конфликт Lorebook · INTERMEDIATE

Проверка: выпишите из записей Lorebook всё, что касается внешности, биографии и отношений персонажа, и сравните с Description. Расхождение в факте (возраст, имя, событие) модель разрешит в пользу того блока, который попал в контекст первым, — и карточка начнёт противоречить себе.

AP-14 · Нарушение контекстного окна · INTERMEDIATE

Что делать: минимальная конфигурация для 4K-контекста — System Prompt 80–100, Description 150–200, два Examples вместе 130–160, Greeting 50–80. CoT, интерпретации OCEAN и Lorebook отключаются, а не сжимаются до нечитаемого.

AP-15 · Вложенные якоря · EXPERT 
❌ Вложенный: "Когда лгут → если уже лгали раньше → хлопает дверью → кричит: «Вон!»"
✅ Атомарные: "Когда лгут → сжимает челюсти → голос становится тише"
           + "Когда обнаруживает ложь повторно → хлопает дверью → уходит в другую комнату"

15 анти-паттернов покрывают самые частые ошибки сборки. Симптом → причина → исправление. Наиболее частые: AP-3 (голос в Description), AP-9 (сломанная SPINE), AP-15 (вложенные якоря).

Налог на письменность (Script Tax)

ПРАВИЛО: Script Tax (налог на письменность) — для нелатинских письменностей (Cyrillic, CJK) бюджет в токенах и в символах расходится: на 12B-моделях с 32K словарём 1 кириллический символ ≈ 1.5–2 токена; на ≥128K словаре и API стоимость приближается к латинской. Поэтому бюджет считается в двух единицах — символы и токены по классу токенизатора; одно число из другого не выводится. Порог: ≥128K словаря → Script Tax несущественен.

Практическое следствие для бюджета: русская карточка на 32K-словаре идёт по нижней границе диапазона бюджета; на ≥128K-словаре и API — Script Tax не меняет расчёт.

Язык системного промпта

Правило языка (включая RP-контент — всегда на языке карточки) и его пороги — ниже.

ПРАВИЛО: Язык SP (Identity + Anti-godmoding + CORE DIRECTIVES + Tone Frame + Format Lock) — многоуровневый по модели:

  • 12B со словарём <64K (ранние Llama 2, Qwen 1.x, ранний Mistral): английский — исторически стабильнее (смещение обучающей выборки ранних моделей).
  • 12B–14B актуальных поколений со словарём ≥128K (Gemma 3 12B, Mistral Nemo, Qwen 2.5 14B): английский оптимален, но язык карточки допустим — разрыв несущественен.
  • 32B+ и API: язык карточки предпочтителен — модель полностью мультиязычна, единый язык SP и RP улучшает консистентность (нет переключения контекста между инструкцией и контентом).

Пороговое правило: если модель имеет ≥128K словаря и нативную поддержку языка карточки — используйте язык карточки для всего SP. Если нет — используйте английский для SP, язык карточки для RP-контента.

API-обёртки: <claude_info> и [SYSTEM NOTE]

API-модели (Claude, GPT-4) поддерживают специфичные форматы инструкций, которые недоступны или работают иначе на open-source моделях. Эти блоки размещаются:

  • В начале Description (рекомендуется для Claude);
